## 一、飞书通道现状

### 1.1 配置是怎么开的

`config.yaml` 里**没有** `platforms.feishu` 段——只有 webhook：

```yaml
# %LOCALAPPDATA%\AppData\Local\hermes\config.yaml:261-266
platforms:
  webhook:
    enabled: true
    extra:
      port: 8644
      secret: hermes...9b2c
```

`grep -n -i "feishu" config.yaml` 全文件只命中 1 行，且是无关的 skill 名（`:155 desktop-feishu-mirror`）。

**飞书是靠 `.env` 里的凭据自动启用的**，不是靠 config.yaml：

| 项 | 证据 |
|---|---|
| `.env` 里有 `FEISHU_APP_ID` / `FEISHU_APP_SECRET` / `FEISHU_ALLOWED_USERS` / `FEISHU_CONNECTION_MODE` / `FEISHU_DOMAIN` | `grep -oE "^[A-Z_]+" .env` 只取变量名，未取值 |
| 启用规则 | `plugins/platforms/feishu/gateway_env.py:8` `ENV_ENABLE_CREDENTIALS = ("FEISHU_APP_ID", "FEISHU_APP_SECRET")`；`gateway/config_env.py` 的 `_enable_from_env()` 在 `platforms.feishu.enabled` 未显式写 false 时，凭据在环境里即自动启用 |
| `config.yaml` 没有 `platforms.feishu.enabled: false` | 同上 grep 结果 |

> ⚠️ 含义：**只要 `.env` 里的凭据还在，飞书就会自动开**。反过来说，要彻底关掉必须显式写 `enabled: false`，删 `.env` 变量反而可能被 `config.yaml` 之外的路径重新拉起。

### 2.3 怀恩生成的文件怎么送过去？

两条路，都不需要改 Hermes 源码：

**路 A — agent 在回复里写 `MEDIA:`（推荐，agent 自己就能触发）**

适配器的 system prompt 提示原文（`plugins/platforms/feishu/adapter_hint.py`）：

> "You can send media files natively: include `MEDIA:/absolute/path/to/file` in your response.
> Images (.jpg, .png, .webp) are uploaded and displayed inline, audio files as native voice messages
> ... and other files as attachments."

怀恩侧要做的（**属于前台代码改动，本次未做**）：让 agent 在产出文件后，把路径标成 `MEDIA:C:/...` 而不是当前的 `[[FILE:路径]]`。

> **注意两者语义不同**：
> - `[[FILE:路径]]`（怀恩现在的约定，`huaien/bridge.py:37`、`parse_artifacts` 在 `:54`，UI 在 `huaien/app.py:342` 用 `os.startfile` 双击打开）= **只给本机 UI 看的卡片**
> - `MEDIA:/绝对路径` = **给飞书看的原生附件**
>
> 两者可以并存：前台卡片照旧显示双击打开，同时给飞书推一份附件。

**路 B — 前台/脚本主动推（不依赖 agent 记不记得写标记）**

```bash
hermes send --to "feishu:<FEISHU_CHAT_ID>" "MEDIA:C:/path/to/report.pdf"
hermes send --to "feishu:<FEISHU_CHAT_ID>" "[[as_document]] MEDIA:C:/path/to/shot.png"
```

`[[as_document]]` 强制以未压缩文件形式投递（`hermes_cli/send_cmd.py:45-46`）。

**关键点**：`hermes send` 的飞书路径是 `_standalone_send`（`adapter.py:4312`）——**它 new 一个临时适配器直接调飞书 HTTP API，不依赖 gateway 进程在跑**。所以即使 gateway 挂了，脚本/定时任务照样能把文件推出去。

### 2.4 一个架构事实：飞书挂的是 default profile，不是怀恩的 huaien profile

- routing 的 session_key = `agent:main:feishu:dm:...` → **main（default）profile**
- `profiles/huaien/config.yaml` **没有** `platforms` 段
- `profiles/huaien/.env` **没有**任何 `FEISHU_*` 变量

→ **飞书机器人的人格是后台 default 那套（结论先行 + H2 分段），不是怀恩的极简人格。** 两个 profile 的记忆靠 `scripts/sync_memory.py` 条目级对齐。

如果要让飞书说话像怀恩（话不多、答完就停），得在 `huaien` profile 也配一份飞书凭据 + 独立 app，否则两条路的人格会不一致。

### 3.3 ⚠️ 关键限制：**普通微信群基本不通，只有私聊可靠**

这是官方文档里写死的警告（`website/docs/user-guide/messaging/weixin.md:19-27`），源码里也有一份（`adapter.py:1303-1308` `_WEIXIN_GROUP_NOTE`）：

> "QR login connects an iLink bot identity (e.g. `<ILINK_BOT_ID>`), **not** a fully scriptable ordinary personal WeChat account. Consequences:
> - The iLink bot identity generally **cannot be invited into ordinary WeChat groups** the way a normal contact can.
> - iLink typically **does not deliver ordinary WeChat group events** (including `@`-mentions of the personal account used for QR login) to the gateway for most bot-type accounts.
> - `@`-mentioning the personal WeChat account used to scan the QR code is **not** the same as `@`-mentioning the iLink bot — the bot is a separate identity.
>
> In practice, **most deployments only get DMs to the iLink bot working reliably**."

源码版原文（`adapter.py:1304-1308`）：
> "QR login connects an iLink bot identity (e.g. ...@im.bot), not a scriptable personal WeChat account. Ordinary WeChat groups typically cannot invite an @im.bot identity, and iLink does not deliver ordinary-group events to most bot accounts."

**所以**：用户拿微信**私聊**机器人 → 可行（且不需要公网 IP，国内稳定）；用户想把机器人**拉进普通微信群** → 基本走不通。

### 3.4 企业微信 `wecom`：个人身份走不通

**前提条件**（官方文档 `website/docs/user-guide/messaging/wecom.md:23-27`）：

1. 一个 **WeCom 企业组织账号**（带管理后台权限）
2. 在管理后台 **创建一个 AI Bot**
3. 拿到 Bot ID + Secret

**凭据**（`plugins/platforms/wecom/plugin.yaml`）：`WECOM_BOT_ID`（必填）、`WECOM_SECRET`（必填）、可选 `WECOM_WEBSOCKET_URL`。

**扫码建机器人**（文档 `wecom.md:31-39`）：
```
hermes gateway setup     → 选 WeCom → 用企业微信 App 扫码 → 自动创建带正确权限的 bot 应用并保存凭据
```
手动路径：管理后台 → 应用 → 创建应用 → **AI Bot** → 复制 Bot ID / Secret。

**传输**：WebSocket `wss://openws.work.weixin.qq.com`（`adapter.py:50` `DEFAULT_WS_URL`）→ **不需要公网 IP**。
**群聊支持**：`wecom.md:148-159` 有 group_policy（open/allowlist/disabled）+ 每群发送者白名单 → **企业微信群里能用**。

### 3.5 企业微信**群机器人 webhook**：Hermes **不支持**

用户问的是「群机器人 webhook」（`https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx` 那种）：

```
$ grep -rn "webhook/send" plugins/ gateway/
（无输出）
```

Hermes 唯一用到 `qyapi.weixin.qq.com` 的是 `plugins/platforms/wecom/callback_adapter.py:48-49`：
```
_SEND_URL  = "https://qyapi.weixin.qq.com/cgi-bin/message/send?access_token="
_TOKEN_URL = "https://qyapi.weixin.qq.com/cgi-bin/gettoken"
```
→ 那是**自建应用**的主动发消息 API（需要 Corp ID/Secret/Agent ID/Token/EncodingAESKey），**不是群机器人 webhook**。

**结论：Hermes 现有的企业微信路径是「AI Bot（WebSocket）」和「自建应用（HTTP 回调）」两种，都不是群机器人 webhook。**
而且群机器人 webhook 本身是**单向**的（只能往群里发，收不到消息），就算自己接也解决不了"手机→PC 发消息"。

### 3.6 `wecom_callback`（自建应用）为什么不适合用户

官方文档 `wecom-callback.md`：

- **Prerequisites**："A **publicly reachable server** for the callback URL (or a tunnel like ngrok)" ← 与 §4 的公网不可达直接冲突
- **Limitations**：不支持流式、无 typing 指示、**入站仅支持文本**（图片/文件/语音未实现）、回复延迟 3–30 分钟、**单条 2048 字节**（中文约 680 字，长的要拆多条）
- 还要企业微信管理后台 + AES-CBC 加密回调 + SHA1 签名

| 问题 | 答案 |
|---|---|
| 个人微信有没有官方机器人 API？ | **有**。腾讯 iLink（微信 ClawBot 插件，2026-03-22 发布），首个官方合法个人号 Bot API。Hermes **官方支持**（`plugins/platforms/weixin/`） |

### 4.1 出口 IP

### 4.2 STUN 复测（本次实测，修正此前"全部超时"的说法）

### 4.3 网络拓扑：**双层 NAT，PC 没有公网 IP**

```
$ ping 192.168.x.x          → 0% 丢包，TTL=128（本地 mifi）
$ ping 192.168.x.x       → 0% 丢包，TTL=255
$ tracert -d 223.5.5.5
  1    28 ms   22 ms   22 ms  192.168.x.x      ← 第一跳是 RFC1918！
$ tracert -d 117.136.38.164
  1    33 ms   22 ms   26 ms  192.168.x.x
$ Get-NetRoute -DestinationPrefix '0.0.0.0/0'
  NextHop=192.168.x.x  InterfaceAlias=以太网 4
$ arp -a
  192.168.x.x   00-b4-b4-b4-b4-b4
```

**读法**：
1. PC = `192.168.x.x/24`（以太网 4），默认网关 = `192.168.x.x`（mifi 的 LAN 口，MAC `00-b4-b4-b4-b4-b4`）
2. 路由器的 web 后台标题页 JS 里 `var g_platformName = "mifi"` → 这是**随身 WiFi / 移动热点设备**，靠蜂窝网上行
3. 第一跳 `192.168.x.x` 是 **RFC1918 私网地址** → 说明 **mifi 的上行口拿到的也是私网 IP**，再往上是运营商 NAT
4. 所以 `117.136.38.164` 是**运营商的共享出口**，不是本机独占的公网 IP

**结论：PC 位于「PC NAT → mifi NAT → 运营商 NAT」三层 NAT 之后，本机没有任何可被入站访问的地址。**

### 4.4 路由器 UPnP / NAT-PMP：**两个都没有**

| 测试 | 命令 | 结果 |
|---|---|---|
| SSDP 发现 | UDP M-SEARCH `239.255.255.250:1900`, `ST: ssdp:all`, 5s 窗口 | **0 个设备响应** |
| NAT-PMP | UDP `192.168.x.x:5351`，发 `\x00\x02`（Public Address Request） | **TimeoutError** |
| IGD 描述文档 | `http://192.168.x.x/{rootDesc.xml, desc.xml, upnp/desc.xml, WanIPConnection.xml, IGD.xml, description.xml}` | **全部 404** |
| 路由器后台 | `http://192.168.x.x/` | **200 OK**（`g_platformName="mifi"`），管理接口 `xml_action.cgi` 返回 `login_status=UNAUTHORIZED`（需登录，未尝试破解） |
| 端口 | TCP 80 **OPEN** / TCP 443 closed | 只有 HTTP 后台 |

→ **没有任何自动端口映射机制**。mifi 是随身 WiFi 设备，普遍不带 UPnP。

### 4.5 Windows 防火墙：该网卡是 **Public** 档

→ **即使监听 0.0.0.0，Public 档默认也拦外部入站**，必须显式加放行规则。

### 4.7 §4 小结：已证实 vs 无法本地证实

**✅ 已证实（本地实测）**

| 事实 | 证据 |
|---|---|
| 出口 IP `117.136.38.164`，中国移动上海段 | `curl ifconfig.me` + `ipinfo.io` |
| 不在 CGNAT `100.64.0.0/10` | IP 段判定 + STUN 两服务器交叉验证一致 |
| **PC 无独立公网 IP**（mifi 上行是 `192.168.x.x` 私网） | `tracert` 第一跳 + `arp` + mifi 后台 `g_platformName="mifi"` |
| UPnP / NAT-PMP **均不可用** | SSDP 0 响应；NAT-PMP 超时；IGD 描述文档全 404 |
| 路由器只开 80，后台需登录 | TCP 80 OPEN / 443 closed；`xml_action.cgi` → `UNAUTHORIZED` |
| 局域网 IP `192.168.x.x/24` | `Get-NetIPAddress` |
| dashboard 9119 **只绑 127.0.0.1**，局域网访问被拒 | `curl http://192.168.x.x:9119/` → `000`；`hermes serve --status` 显示 `--host 127.0.0.1` |
| webhook 8644 绑 `0.0.0.0`，局域网可达 | `curl http://192.168.x.x:8644/` → `404`（连接成功） |
| 该网卡防火墙 = Public 档，默认阻入站 | `Get-NetConnectionProfile` + `Get-NetFirewallProfile` |

**❌ 无法本地证实（必须外部网络测试）**

| 待证事项 | 为什么本地测不了 | 怎么测 |
|---|---|---|
| 手机 4G/5G 能否直连 PC 的某个端口 | 本机自测是 hairpin/loopback，系统性低报失败（`remote-access-paths.md:44`） | 手机切流量 → 访问 `http://117.136.38.164:<port>` |
| 运营商是否给本机分配了可入站的 1:1 公网地址 | mifi 上行是私网 → 极大概率不是，但只有从外部打才知道 | 手机流量访问 + 抓包 |
| 高位端口（50022+）是否被上游封 | 本地无从判断 | 同上 |

**最终判断：「PC 起 HTTP 服务 + 手机用 4G/5G 直连」这条路，在当前网络下不可行**（双层 NAT + 无 UPnP + Public 防火墙三重叠加）。要用公网，**必须走中继/组网**。

## 六、推荐排序 + 落地动作

### 🥇 第 1 名：飞书当手机端（修好入站）

**为什么排第一**：出站已经实测通了（4/4），只差**一个权限 + 一次重新发布**。不装任何软件、不要公网 IP、国内最稳、文件/图片/表格/卡片全都原生支持。

**落地动作**

```bash
# ① 补权限：打开这个链接（一键授权，tenant scope）
#    https://open.feishu.cn/app/<FEISHU_APP_ID>/auth?q=im:chat:readonly,im:message:send_as_bot,im:message.p2p_msg,im:message.group_at_msg&op_from=openai&token_type=tenant
#    缺的两个：im:message.p2p_msg（私聊入站）、im:message.group_at_msg（群 @ 入站）
#    （该链接来自 scripts/probe_feishu_scopes.py 的输出，是一次性的授权链接）

# ② 授权后必须重新发布版本，否则权限不生效
#    开放平台 → 版本管理与发布 → 创建版本 1.0.1 → 申请发布
#    ⚠️ reference 明确警告：授权后不重新发布 = 权限不生效

# ③ 复验权限
cd "%LOCALAPPDATA%/AppData/Local/hermes/cache/scratch"
"%LOCALAPPDATA%/AppData/Local/hermes/hermes-agent/venv/Scripts/python.exe" \
  "%LOCALAPPDATA%/AppData/Local/hermes/skills/hermes-internals-bypass/scripts/probe_feishu_scopes.py"
#    期望：MISSING 列表为空

# ④ 用户亲自验证入站（这一步本地代替不了）
#    在飞书里给「Hermes-work」机器人发：/help
#    然后看日志有没有入站：
grep -i "platform=feishu" "%LOCALAPPDATA%/AppData/Local/hermes/logs/gateway.log" | tail -5

# ⑤ 设 home channel，省掉每次写 chat_id

# ⑥ 顺手补上飞书的读权限（入站媒体/文档要用）
#    权限里补 im:resource（user scope 已勾，但 tenant 也建议补）
```

**验证清单（按 reference 的五步端到端）**
1. `hermes gateway status` → 显示 feishu 已启用 ✅（当前已满足）
2. 前台日志出现 connected ✅（当前已满足，12:09:20）

4. 回复通顺（`/help` 是干净测试）← 待用户验证

### 🥈 第 2 名：局域网 Web（同一 WiFi）

**为什么排第二**：完全在本机，不依赖任何外部服务，最稳；但**必须同 WiFi + PC 开机**，且需要一次前端开发（怀恩现在是 Tkinter）。

**落地动作**

```bash
# ① 固定 session token（否则每次重启手机 cookie 失效）
python -c "import secrets; print(secrets.token_urlsafe(32))"
#    把输出追加到环境文件，键名 HERMES_DASHBOARD_SESSION_TOKEN
#    （不要在终端里回读环境文件的值——会触发 secrets 保护锁）

# ② 绑定到局域网 + 钉死端口（dashboard 已有 password provider，鉴权直接生效）
hermes serve --host 0.0.0.0 --port 9119
#    注意：--insecure 已废弃，非回环绑定强制要 auth provider（用户已配好）

# ③ Windows 防火墙放行（该网卡是 Public 档，默认阻入站）
powershell -NoProfile -Command "New-NetFirewallRule -DisplayName 'Hermes 9119 LAN' -Direction Inbound -Protocol TCP -LocalPort 9119 -Action Allow -Profile Any"
#    想更严就换成 -Profile Private + 把网卡改成 Private：
powershell -NoProfile -Command "Set-NetConnectionProfile -InterfaceAlias '以太网 4' -NetworkCategory Private"

# ④ 局域网自测（确认绑定生效；注意回环会自动放行，这个测试只证明绑定不证明鉴权）
curl -o /dev/null -w "%{http_code}\n" http://192.168.x.x:9119/
#    期望 302 或 200（不再是 000）

# ⑤ 手机连同一 WiFi，浏览器打开
#    http://192.168.x.x:9119
#    → 应弹 basic auth（用户名 zhao）→ 输密码 → 进 dashboard
#    这台机器的 dashboard 密码哈希在 config.yaml dashboard.basic_auth
```

**怀恩本身上手机**（额外开发量）
- 把 Tkinter UI 抽成 Web UI，做成 PWA（`manifest.json` + service worker），手机「添加到主屏幕」
- 或先不折腾：直接用 Hermes 官方 dashboard 的 `/chat` 页当手机端（它内嵌 xterm.js 跑真实 TUI）

### 🥉 第 3 名：组网穿透（备用，只在 (a)(b) 都不够时）

**为什么排第三**：本机现状最差（ZeroTier 是坏壳），要装软件，ZeroTier/Cloudflare/Tailscale 默认都走境外（与"不走境外流量"冲突），且自建 CN moon 的前提（有公网 IPv4 的国内机器）本机不满足。

**落地动作**

```bash
# 方案 c-1：蒲公英（国内中继，不走境外，免费档 1 设备 3 成员）
#    官网 https://pg.oray.com  → 注册 → 装客户端 → 加入网络
#    PC 端装完拿到虚拟 IP，手机端装同一个网络 → 互相能访问
#    然后 hermes serve --host 127.0.0.1 --port 9119 + 蒲公英映射

# 方案 c-2：重装 ZeroTier（当前是坏壳）
winget install -e ZeroTier.ZeroTier --accept-package-agreements --accept-source-agreements
# ⚠️ 三个坑（references/zerotier-windows-recipe.md:18-22, 60-63）：
#   1) 必须先 takeown + icacls 授权 authtoken.secret，否则 zerotier-cli info 报权限拒绝（头号坑）
takeown /F "C:\ProgramData\ZeroTier\One" /R /A
icacls "C:\ProgramData\ZeroTier\One" /inheritance:e
icacls "C:\ProgramData\ZeroTier\One\authtoken.secret" /grant "%USERNAME%":R
#   2) 1.16+ 必须注册 my.zerotier.com 中央账号并创建网络，拿到 16 位网络 ID，没有纯 CLI 路径
#   3) 默认 planet 在境外 → 违反不走境外约束；要国内 moon + allowGlobal=false
zerotier-cli info            # 期望 200 info <node-id> <version> TUNNELED
zerotier-cli join <16位网络ID>  # 期望 200 join OK
#   然后去 https://my.zerotier.com → Members → 勾选 → Authorized

# 方案 c-3：Tailscale（最省事，但失败时回落境外 DERP）
winget install Tailscale.Tailscale
tailscale up
tailscale status
tailscale ip -4

# 方案 c-4：Cloudflare Tunnel（最省事但流量走海外边缘）
winget install Cloudflare.cloudflared
cloudflared tunnel --url http://127.0.0.1:9119
```

**无论哪条，公网入站的最终验证只有一种**（`references/remote-access-paths.md:44` + `dashboard-exposure.md` 的验证矩阵）：

> **手机切到 4G/5G 流量**（不能是 WiFi）→ 打开 `http://<公网地址>:9119` → 应先弹鉴权再进 dashboard。
> 本机 curl 一律是回环或 hairpin，**能过不代表真能通**。

## 结语

**飞书是这三条路里唯一"管道已经通、只差开阀门"的一条。**

出站四种格式实测全通、传输层 connected、机器人在册、有过 2.5 个月前的真实私聊记录 —— 这些都是硬证据。
缺的就是一个 tenant 权限（`im:message.p2p_msg`）加一次重新发布。补完之后，用户在飞书里发一条 `/help` 就能闭环。

**公网直连这条路，就当前网络条件（mifi + 运营商 NAT + 无 UPnP + Public 防火墙）而言是关死的**，不要再在这上面花时间。
局域网路线是可靠的第二选择，但需要一次前端改造（怀恩现在不是 Web）。
组网穿透是第三选择，本机 ZeroTier 还是个坏壳，且默认方案都要走境外。

> 内部 reference 的一条硬规矩，正好是本次调研的收尾：
> **"没让用户从真实网络测过，就不能说某条路'能用'。"**
> 所以 (a) 的入站、(b) 的手机访问、(c) 的隧道穿透 —— 三者都留了"用户亲自验证"的验收格，不替用户下结论。
