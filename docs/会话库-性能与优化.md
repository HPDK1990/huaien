# 会话库 — 到底会不会慢

> 用户 2026-10-30: *"会话库会越来越慢是什么情况？会有影响么？怎么优化？"*

## 一、实测数据（不是推测）

```
state.db            314.4 MB
messages            50134 条
sessions            147 个
正文字符            44,447,272 (4400 万)
```

| 操作 | 耗时 | 评价 |
|---|---|---|
| `COUNT(*)` 全表计数 | **2.0 ms** | 很快 |
| FTS5 全文索引搜索 | **1.0 ms** | 很快，索引是好的 |
| `LIKE '%关键词%'` 全文扫（最坏情况） | **150.6 ms** | 可接受 |
| `sessions` 全表排序 | 1.3 ms | 很快 |

## 二、结论：**数据库不慢，慢的是上下文**

我之前说"会话库会越来越慢"是**不准确的**，实测下来：

- **查询本身毫秒级** —— 因为有 FTS5 索引，搜索根本不走全表。
- 真正会变慢的是**每次对话要装多少上下文**：50134 条消息 / 4400 万字符，
  续接会话时历史越长，模型响应越慢、token 越贵。
- **磁盘占用会一直涨** —— 314 MB 还在长，备份一次要 96 秒。

**所以"影响"是这三个，不是数据库卡：**

| 影响 | 严重度 | 说明 |
|---|---|---|
| 上下文变长 → 响应变慢变贵 | ⭐⭐⭐ | **真正的成本来源** |
| 磁盘占用涨 | ⭐⭐ | 314 MB，备份 96 秒 |
| 数据库查询变慢 | ⭐ | **目前没这问题**，FTS 索引扛住了 |

## 三、为什么 314 MB 里有一大块是冗余

体检脚本查到：

```
fts_external_content: false
```

**FTS 索引还是旧布局 —— 它自己存了一份消息的完整副本**（含 tool_result 的大 JSON）。
官方文档对 `optimize-storage` 的说明：

> Rebuild the full-text search index in the compact v23 external-content layout.
> On large databases this **reclaims a large fraction of state.db**
> (the old layout stored duplicate copies of every message and indexed tool output).
> **No conversation data is changed**; only the search index is rebuilt.

**只重建索引，不动任何对话数据**，而且可以中断后重跑（会从断点续）。

## 四、怎么优化 —— 三条路

### 路线 1（推荐）：跑一次 `optimize-storage` 回收空间

```bash
hermes sessions optimize-storage --yes
```

**但它会拒绝在 gateway 运行时跑**（正确保护 —— 在活着的写入方下面重建库，
会让所有 agent 报 "retired state.db-wal error"）。

**已经做好一键脚本**：`scripts\优化会话库.bat`
（停 gateway → 优化 → 起 gateway；必须由网关之外的进程执行）

**怎么跑**（双击，或）：
```bash
schtasks /Create /TN "HuaiEnOptimizeDb" /TR "cmd /c <PROJECT_ROOT>\scripts\优化会话库.bat" /SC ONCE /ST 23:59 /F
schtasks /Run /TN "HuaiEnOptimizeDb"
```

**代价**：中断 gateway 约 2-5 分钟（314 MB 的库重建索引 + VACUUM）。
**收益**：官方说"large fraction"，314 MB 里索引占的那份冗余能收回来。

### 路线 2：清理老会话（真正减少上下文）

```bash
hermes sessions prune --older-than 60d --dry-run    # 先看会删什么
hermes sessions prune --older-than 60d --yes        # 真删
hermes sessions archive --older-than 30d            # 只是软隐藏，不删
```

**注意**：`prune` 是**真删**（连消息一起），用户的"危险操作铁律"要求先 dry-run 看清清单。
目前 147 个会话里 **archived 只有 4 个** —— 归档几乎没在用，**空间主要是老会话堆出来的**。

### 路线 3：只监控，不动（**现在就在做**）

`scripts/db_health.py` —— **纯只读**体检，已经接进回归看门狗：

```
{"size_mb": 314.4, "messages": 50134, "sessions": 147,
 "ms_count_all": 2.0, "ms_fts_search": 1.0, "ms_like_scan": 150.6,
 "fts_external_content": false}
```

阈值：文件 > 500 MB 或 全文扫 > 800 ms 才提醒。**超了再动手，不用现在折腾。**

## 五、我的建议

**现在不动大优化。** 理由：

1. **实测不慢** —— 数据库查询毫秒级，没有"越来越慢"这个现象。
2. 314 MB 完全能接受 —— 备份 96 秒，磁盘还有 268 GB。
3. 真要优化，`optimize-storage` **不需要删任何数据**（只重建索引），风险极低，
   但会中断 gateway 几分钟 —— 挑个你不在用的时候跑最合适。

**已经做的**：体检脚本接进回归看门狗，每 6 小时自动看一眼，超阈值才提醒。
