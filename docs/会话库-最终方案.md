# 会话库 — 批判性修改后的最终方案

> 用户 2026-10-30: *"会话库现在顶端agent是如何进行优化的？想include，codex和你自己hermes。
> 你给的优化方案我感觉都不好。先看看大家是怎么弄的。再弄优化方案，然后批判性修改优化方案，最后再改。"*

**过程**：先派子代理横向调研 Claude Code / Codex / Hermes → 主代理逐条复核 →
**推翻我自己之前写的三个错误论断** → 出最终方案 → 副本实测 → 执行。

横向对比全文见 `docs/调研-会话存储对比.md`（790 行，含全部证据来源）。

## 一、我之前写错了三个地方（用户的直觉是对的）

我上一版 `会话库-真问题.md` 里有三个论断，**全部是错的**，被实测和源码推翻：

| 我之前写的 | 实际 | 错在哪 |
|---|---|---|
| "压缩压根没触发过" | **压缩一直在工作**：54 条摘要行 + 27407 条归档行 | 我拿 `auto_archived=0` 当压缩证据 —— 那是**闲置归档标记**，跟压缩无关 |
| "压缩失败计数全 0 = 没触发" | **0 的含义是"从未失败"** | 我把状态读反了 |
| "让压缩真的能跑（打开 idle_compact_after_seconds）" | 压缩本来就在跑，**打开它反而危险** | 压缩失败时 Hermes 是**冻结会话**（`frozen at its size until /compress or /new`），不是降级 |

**还有一个半对**：

| 我之前写的 | 实际 |
|---|---|
| "FTS 索引还是旧布局" | **对一半**：`messages_fts` 已是 v23 外部内容模式（不存副本）；**但 trigram 索引还是 v1**（多索引了 `tool_calls` 列）→ 那 116 MB 就是它 |

## 二、三家怎么做的（结论摘要）

| | Claude Code | Codex CLI | **Hermes** |
|---|---|---|---|
| 介质 | append-only JSONL | 日期分区 JSONL + SQLite 元数据 | 单 SQLite |
| 全文索引 | ❌ | ❌ | ✅ FTS5 外部内容 |
| **历史 ≠ 上下文** | `type:"summary"` 条目 | `compacted` 记录 | **`messages.active` 布尔位** |
| 自动清理 | **默认 30 天直接删** | 只归档不删 | 默认关 |

**"历史不等于上下文"这个区分，三家都实现了**，Hermes 的实现最干净：
`active=1` 的 14290 条送进模型，`active=0` 的 36092 条完整留着供搜索/审计。

**Codex 是反面教材**：`compacted` 记录把全量历史重复嵌进去，
单文件涨到 1.95 GB、全库 755 GiB（openai/codex#24948、#34337）。
Hermes 用"摘要独立成行"（`_compressed_summary=1`）刻意避开了这个坑。

**Claude Code 未在本机安装**，其结论来自官方文档与第三方源码分析，**无本机实测**。

## 三、真问题到底是什么

**"库大"和"会慢"是两件事。** 实测：

```
全表 COUNT(*)            2.0 ms
FTS5 全文索引搜索        1.0 ms
LIKE '%关键词%' 全文扫   150.6 ms
```

**查询全在毫秒级。** 真正会变慢的是「在一条长会话里一直聊」——
这个会话已经 492 条消息，历史一直往上下文里堆，迟早撞上 50% 压缩阈值。

**而磁盘空间的真正浪费在别处**（`dbstat` 实测）：

```
messages                135 MB  ← 真数据
messages_fts_trigram   116 MB  ← 冗余! v1 布局多索引了 tool_calls 列  ← 最大头
messages_fts            25 MB  ← v23 外部内容模式 ✅
state_meta              16 MB  ← 全是 gateway.admission.result 缓存 (可再生)
```

## 四、最终方案（按优先级）

### P0 — 备份（先做，无风险）

`state.db` → `<PROJECT_ROOT>\versions\backup\state_<时间戳>.db`

### P1 — `optimize-storage`（回收 ~94 MB）

**源码依据**（`hermes_state_search.py:658-664`）：

> Repair an older FTS layout into the current v23 shape: legacy-v22 inline →
> external-content, or a v23 `messages_fts_trigram` that still stores `tool_calls`.
> **No conversation data is changed; only the search index is rebuilt.**

当前代码的 trigram 布局就是 `(rowid, content, tool_name)` —— **没有 `tool_calls` 列**，
而本机还是带这列的 v1 → **正是它要修的情况**。

**副本实测（真库全程只读）**：

```
317.4 MB -> 220.8 MB   省了 96.6 MB (30.4%)
trigram   117.5 MB -> 26.4 MB   省了 91.1 MB
messages  50216 -> 50216  ✅      chars 44825653 -> 44825653  ✅
summaries 54 -> 54  ✅            archived 36092 -> 36092  ✅
FTS 搜索命中 50 条 ✅              耗时 145 秒
```

**代价**：必须停所有持有 `state.db` 的进程（gateway + Desktop + dashboard + 怀恩）。
**收益**：~94 MB。**不删任何一条对话。**

### P2 — 清 `state_meta` 的网关回执（再回收 ~19 MB）

`gateway.admission.result.v1.*` 共 115 行 / 1405 万字符 —— 是**网关对某一轮对话的
准入判定结果快照**，**可再生**（下次同样的判定会重新生成）。

**删掉不影响**：任何对话内容、搜索、会话列表。

**必须先停 gateway** —— 否则它会立刻再写回去；更糟的是正在进行的 turn 的回执被删，
那一轮无法重放。所以这一步跟 P1 放在同一个停机窗口里。

### P3 — 让 cron 任务每次开新会话（减缓未来增速）

`助手榨干器-*` / `怀恩项目-定时检查-*` 这些 cron 会话，每个独立攒 40–60 万字符，
且几乎不会被再次打开。

**做法**：cron 每次跑完开新会话，老会话自动归档。
**归档不删数据** → 用户想搜还能搜；库的增速自然趋缓。
**这条不动任何 Hermes 源码、不改配置。**

### P4 — 归档老会话（**当"整理"，不当"优化"**）

`hermes sessions archive` 是软隐藏，**回收不了空间**（磁盘占用不变）。
148 个会话里绝大多数是 cron 产出的，"闲置"判定意义不大。
**以后再说。**

## 五、明确不该做的（用户的历史比这点空间值钱）

| 不该做 | 理由 |
|---|---|
| ❌ `hermes sessions prune` | **回收 0 字节**（本机全部会话 < 90 天），却会砍掉关键项目历史；被删会话的消息全删、`parent_session_id` 置 NULL |
| ❌ 手工 `DELETE FROM messages WHERE active=0` | 能回收 45.4 MB，但删掉的是**用户唯一的历史副本** —— `active=0` 只表示"不送进模型"，不是"没用" |
| ❌ 改 `compression.threshold` / `abort_on_summary_failure` | **会改变 agent 行为**。压缩失败时 Hermes 是**冻结会话**，不是降级；打开 `abort_on_summary_failure` 会让整段历史卡住 |
| ❌ 开 `auto_prune` | 这是删数据，默认 `false` 是有意的（源码注释："deleting history is opt-in"） |
| ❌ 动 `sessions.retention_days` | 本机所有会话都在 90 天内，改它对现状零影响，只是给未来埋一个删除定时器 |
| ❌ 单独跑 VACUUM | 只回收 3.9 MB（1.2%），因为 freelist 只有 10 页 |

## 六、执行方式

**必须脱手** —— gateway 不能从自己进程里停，`optimize-storage` 也拒绝在有活跃写入者时跑。
源码警告：

> rewriting the store under a live writer can leave every agent refusing turns
> until all writers are stopped

所以走 **schtasks 计划任务**（在网关进程树之外执行）：

```
scripts\优化会话库完整.bat
  1 备份 state.db
  2 抓基线快照
  3 停 gateway / Desktop / 怀恩 / dashboard
  4 optimize-storage --yes
  5 清 state_meta 网关回执
  6 验证 (条数/字符/FTS/trigram 体积/文件大小)
  7 验证不过 -> 自动还原备份
  8 起 gateway -> 起 Desktop
```

**验证的硬判据**（任何一条不过就还原）：

| # | 判据 | 副本实测 |
|---|---|---|
| 1 | 消息条数不变 | 50216 -> 50216 ✅ |
| 2 | 正文字符数不变 | 44825653 -> 44825653 ✅ |
| 3 | 压缩摘要行不变 | 54 -> 54 ✅ |
| 4 | 归档历史不变 | 36092 -> 36092 ✅ |
| 5 | FTS 还能搜 | 命中 50 条 ✅ |
| 6 | trigram 索引明显变小 | 117.5 -> 26.4 MB ✅ |
| 7 | 文件变小 | 317.4 -> 220.8 MB ✅ |

`fts_layout_drift()` 只作**参考**（布局定义随版本变，检测器口径可能与当前实现有差异）；
真正定生死的是上面七条可量化的硬判据。
