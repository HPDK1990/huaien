## 二、参考：DeepSeek Super-agent 的做法

它的领域模型（`docs/001-domain.md`）核心链路：

```
Source → Trigger → Thread → Eval(Gate 准入 + Assessment 研判) → Decision
       → Ticket(工单 + Mandate 授权) → Assignment(派工)
       → Executor(worker-<ticket-id> 独立 Session + 独立目录)
       → Report(progress/waiting/ready/blocked/failed) → 回原渠道
```

**它是怎么做到"主 Session 不干活的"**（`docs/003-execution.md`）：

> *"The main Session uses `dsh-superagent-router`, with the same 5-second shell and
> job-wait limits and **a smaller tool set for routing**."*

> *"The main Session ... evaluates Triggers, accepts and dispatches Tickets, and replies."*
> —— 主 Session 只做三件事：评估、派工、回复。

**两条它已经踩过并解决的坑，怀恩现在正踩着**：

| Super-agent 的规则 | 怀恩现状 |
|---|---|
| *"A new human message releases a `blocked` or `failed` Ticket to its Executor"* | ❌ blocked 卡要人手动 unblock（我昨天手动解了 2 张） |
| *"the main Session receives no waiting report"* | ⚠️ 主会话会收到 worker 的等待消息 |

**它的 Decision 有四档**：`accept` / `stop` / `ignore` / `unavailable`
—— **明确允许"不接单"**，不是所有触发都要变成工作。

## 三、批判性审查：用户的方案哪里要改

### 🔴 问题 1：「所有问题都是下面做」会**更慢**，不是更快

| 用户问 | 主怀恩自己答 | 派给子 agent |
|---|---|---|
| "现在几点" | **1 秒** | 起 agent 5-30 秒 |
| "刚才那个文件在哪" | 3 秒（read_file） | 30 秒+ |
| "你好" | 1 秒 | 30 秒（起 agent 跑一趟说 hello） |

**主怀恩自己答 = 秒回；全派 = 变成 30 秒。** 用户要的是"第一时间回答"，
**全派恰好违背这个目标**。

### 🔴 问题 2：子 agent 不知道主会话聊过什么

子 agent 是**独立 Session**（superagent 明确叫 `worker-<ticket-id>`），
它看不到主怀恩刚才跟用户聊的内容。全派之后，用户说"刚才说的那个"，
子 agent 会一脸茫然 → **用户得重复交代一遍**，这跟"省事"正好相反。

### 🟡 问题 3：成本与噪音

每个"你好""收到"都起一个 agent = 白烧 token + 刷屏。
superagent 自己的 `Decision` 里就有 `ignore` 这一档 —— **它也不认为该每件事都接单**。

### 🟡 问题 4：「第一时间回答」和「先评估再答」矛盾

评估（判断该派谁）本身要一次 LLM 调用，10-30 秒。
**如果等评估完再回答，就不是"第一时间"。**

**解法**：**主怀恩先秒回一句**（"我来安排"），**再评估派工**。
这跟 superagent 的异步设计一致（*"新输入在当前推理步结束后就处理，
不等后台工具完成"*；Hermes 原生对应 `/steer` 和 `/queue`）。

## 四、方案 v2（批判性修改后）

### 核心原则

**主怀恩 = 路由层，不是无脑全派。**
**"不干活"用裁工具实现（硬约束），不是用 prompt 自觉（软约束）。**

```
用户发消息
  │
  ├─▶ 【第 0 步 · 秒回】主怀恩立刻回一句（不评估、不查文件、不等工具）
  │      "我去办" / "这个我知道" / "要查一下，两分钟给你"
  │
  ├─▶ 【第 1 步 · 评估】该不该派？判据（确定性，不靠感觉）：
  │      要跑命令 / 要读一堆文件 / 要多角色并行 / 要等很久  →  派
  │      一句话事实 / 记忆里就有 / 看板状态直查             →  自己答
  │
  ├─▶ 【第 2 步 · 派工】重活 → 建 Ticket → 派给 worker
  │      worker 独立 Session + 独立目录干活
  │
  └─▶ 【第 3 步 · 回流】worker 报 ready/blocked → 管家推回用户的渠道
```

### 硬约束：裁掉主怀恩的重活工具

`platform_toolsets` 逐个列工具集，所以裁剪是**物理生效**的：

| 渠道 | 工具集 | 理由 |
|---|---|---|
| **weixin / feishu**（手机随手问） | `kanban` `delegation` `memory` `skills` `web` `vision` `session_search` `cronjob` | **主怀恩在这两个渠道上没有 terminal / file / code_execution → 物理上没法自己干重活** |
| **cli**（桌面前台 / PWA） | 保持全量 | 用户在电脑前，可以接受慢；而且 PWA 的 `/api/ask` 走这条 |

**保留 `vision`** —— 用户发照片过来要能看懂（这是"秒答"的一部分）。
**保留 `web`** —— 一句话事实查询，不算"干活"。

### 人格层：SOUL.md 改成路由人格

现在的 SOUL.md 写着：

> *"你有工具可以用: 文件读写、终端命令、代码执行、网络搜索、看图、记忆、看板、
> 子代理、定时任务。用户说的每件事都可以直接做，不需要先请示。"*

**这句是"什么都能干"的根源**，要改成：

> 你是**主怀恩**。你只做三件事：**判断、派工、回复**。
> 重活一律派给下面的 worker（researcher / coder / auditor / default）。
> 你自己只处理秒答级别的：记忆里有的、看板状态、一句话事实。

### 补上 superagent 已有的两条

| # | 机制 | superagent 原文 | 怀恩怎么做 |
|---|---|---|---|
| 1 | **人消息自动释放 blocked 卡** | *"A new human message releases a `blocked` or `failed` Ticket to its Executor"* | 管家巡检：卡 blocked + 卡上有"等上游"注释 + 上游已 done → 自动 unblock。**但要避开用户自己等人决策的卡** |
| 2 | **Attention（待人工决定）** | Report 类型之一；Ticket 阶段 `person / answer` | 主怀恩需要能**问用户一个问题并等回答**，而不是猜。实现：建一张 `waiting` 卡，body 里写问题 |
