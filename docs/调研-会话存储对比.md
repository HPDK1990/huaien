# 调研：Claude Code / Codex CLI / Hermes 的会话存储与上下文管理对比

> 调研日期：2026-10-30
> 调研对象：Claude Code（Anthropic）、Codex CLI（OpenAI）、Hermes Agent（本机 v0.22.2）
> 方法：读三家的源码/官方文档 + 在本机 `state.db` 上做只读实测（所有写操作都在 scratch 副本上做，真库未动）
> 回答用户的问题：*"你给的优化方案我感觉都不好，先看看大家是怎么弄的"*

---

## 0. 摘要：三个结论先说

| # | 结论 | 一句话证据 |
|---|---|---|
| 1 | **三家都做「历史 ≠ 上下文」**，但切分方式不同 | Claude Code 用 JSONL 里的 `summary` 条目；Codex 用 `compacted` 记录；Hermes 用 `messages.active` 布尔位 + `_compressed_summary` 行 |
| 2 | **Hermes 的压缩机制其实一直在正常工作**，之前"压缩没触发过"的判断是错的 | 库里 54 条 `_compressed_summary=1` 的摘要行、27,407 条 `compacted=1` 的归档行，分布在 5 个会话上 |
| 3 | **真正的磁盘浪费是 trigram 索引的一份额外拷贝**，不是消息本体 | 实测：把 trigram 索引从 v1 布局重建到 v3 布局 → **回收 92.2 MB / 29.2%**，且不删任何一条消息 |

> ⚠️ 本报告推翻了 `docs/会话库-真问题.md` 里的两个核心论断（"压缩压根没触发过"、"FTS 索引还是旧布局"）。下文第 3 节给出实测证据。

## 1. Claude Code 怎么存对话历史？

### 1.1 存储位置与格式

**append-only JSONL，不是 SQLite。**

- 路径：`~/.claude/projects/<工作目录路径转义>/<session-id>.jsonl`
  - 转义规则：非字母数字字符全部换成 `-`；超过 200 字符则截断到 200 并追加原路径哈希
  - 证据：Claude Code 官方文档 "Manage sessions" 页 —— *"By default, Claude Code stores transcripts as JSONL at `~/.claude/projects/<mangled-cwd>/<sessionId>.jsonl`"*
- 每行一个 JSON 对象，类型包含 `user` / `assistant` / `system` / `attachment` / `summary` / `custom-title` / `last-prompt` / `content-replacement` / `file-history-snapshot` 等
  - 证据：https://github.com/openedclaude/claude-reviews-claude/blob/main/architecture/09-session-persistence.md （"09 — Session Persistence" 章节，Entry Types 表）
- **append-only 语义，但 resume/rewind 会重写已写过的行**，同一个 `uuid` 会出现多次
  - 证据：https://www.bough.run/docs/format/claude-code —— 实测最大会话 36,676 行 vs 10,964 条去重记录（超过 3 倍虚高），去重规则是按 `uuid` 合并、保留后出现的非空字段
- **本机没有 Claude Code**（`~/.claude/projects` 不存在，0 个 jsonl），所以本节全部依据官方文档与第三方源码分析，无本机实测

### 1.2 有没有索引？

**没有全文/向量索引。** 官方文档明确说 transcript 是给 `--resume` 读的原始日志，要建索引得自己写脚本：

> *"The entry format is internal to Claude Code and changes between versions, so scripts that parse these files directly can break on any release. To build on session data, use `/export` or the script interfaces instead."*
> —— Claude Code 官方文档 "Manage sessions"

搜索历史靠 grep 扫文件，不是 FTS。

### 1.3 有没有压缩/截断/归档机制？—— **有，而且是最早成体系的**

| 机制 | 说明 | 证据 |
|---|---|---|
| **上下文压缩** | `/compact` 把中段对话压成一条 `summary` 条目。支持带参���：`/compact focus on the current implementation plan` | claude-wiki.com/session-persistence.html；compact-plus 架构文档 |
| **Context Collapse 快照**（Tier 4） | 压缩时额外保存 `preservedSegment` 边界，让压缩后还能选择性恢复文件引用 / skill 状态 | claude-wiki.com/session-persistence.html |
| **Tombstone GC** | 失效条目（流式工具执行器产生的孤儿调用）在 **50 MB 阈值**触发回收 | claude-wiki.com/session-persistence.html |
| **Transcript 本地 GC** | `CLAUDE_CODE_TRANSCRIPT_LOCAL_GC` 环境变量，打开磁盘 transcript 本地回收（v2.1.217 引入，未公开文档） | turboai.dev/blog/claude-code-env-vars-v2-1-217；changelogs.core-directive.com |
| **启动时清理** | `cleanupPeriodDays` 控制，默认 **30 天**，启动时扫掉过期 transcript | 官方文档 "All settings" 页 `cleanupPeriodDays` 条目 |

**关键机制：`summary` 是存在同一个 JSONL 里的**——即"压缩后的上下文"和"完整历史"在同一份文件中，靠 `type` 字段区分。模型只吃 summary + 尾部，磁盘上留全量。

### 1.4 怎么处理膨胀？—— **靠"删"，不靠"省"**

- 默认 **30 天**后直接删除 transcript 文件
- `cleanupPeriodDays` 可调，最小 1，**设 0 会校验失败**（要长期保留得设 3650）
- `desktopSessionCleanupPeriodDays` 单独控制 Desktop/Cowork 的 transcript
- 可以 `CLAUDE_CODE_SKIP_PROMPT_HISTORY` 完全关闭写入，或 `claude -p --no-session-persistence` 单次不写
- 证据：官方文档 "All settings" `cleanupPeriodDays` 条目 + "Data usage" 页（*"Local caching: Claude Code clients store session transcripts locally in plaintext under `~/.claude/projects/` for 30 days by default to enable session resumption"*）

> **⚠️ 代价**：这是业界最激进的策略。社区大量 issue 报告"启动 GC 静默删除 transcript"（anthropics/claude-code#62041、#62272、#62959、#63187）。对用户这种"历史要留、能搜"的用法，Claude Code 的默认行为**直接不可用**。

### 1.5 业界还想给 Claude Code 补索引

有第三方项目专门做这件事（如 claude-code-best/claude-code 的 `sessionStorage.ts` 提供 `getTranscriptPath()`），说明"裸 JSONL 无索引"确实是痛点。

## 2. Codex CLI（OpenAI）怎么存？

### 2.1 文件布局

**日期分区的 append-only JSONL "rollout" 文件 + 一个 SQLite 索引。**

```
~/.codex/sessions/YYYY/MM/DD/rollout-<ISO8601>-<uuid>.jsonl
```

- `<ISO8601>` 是开始时间，`:` 换成 `-`（如 `2026-06-12T16-08-36`）；`<uuid>` 就是 session id（UUIDv7，时间有序）
- 子 agent 是**独立的 rollout 文件**，放在同一个日期树里，靠 `session_meta.parent_thread_id` 关联
- 证据：openai/codex 源码 `codex-rs/rollout/src/recorder.rs` —— 注释明确 *"Rollouts are recorded as JSONL"*，并展示了 `~/.codex/sessions/YYYY/MM/DD/rollout-...jsonl` 的构造逻辑
- 证据：neochoon/agenthud `docs/schemas/codex-session.md` —— 记录了 `session_meta` 的完整字段结构（`id`/`timestamp`/`cwd`/`originator`/`cli_version`/`source`/`model_provider`/`base_instructions`）

**本机实测**（`~/.codex/sessions/2026/08/05/rollout-2026-08-05T22-08-17-*.jsonl`，123,484 字节 / 72 行）：

```
lines: 72
top-level: {'session_meta': 1, 'event_msg': 41, 'response_item': 21, 'world_state': 2, 'turn_context': 7}
payload types: {'task_started': 7, 'message': 17, 'user_message': 7, 'agent_message': 7,
                'token_count': 7, 'task_complete': 7, 'thread_settings_applied': 6, 'reasoning': 4}
```

### 2.2 索引：SQLite 只存元数据，**不建全文索引**

本机 `~/.codex/` 下的 SQLite：

| 文件 | 大小 | 内容 |
|---|---|---|
| `state_5.sqlite` | 278 KB | `threads` 表（id/rollout_path/created_at/cwd/title/tokens_used/archived…）、`thread_spawn_edges`、`thread_sections`、`projects` 等 |
| `logs_2.sqlite` | 1.9 MB | `logs` 表（结构化日志行） |
| `goals_1.sqlite` / `memories_1.sqlite` / `queue_1.sqlite` | 小 | 各自功能 |

**关键：`threads.rollout_path` 只是一个路径指针，rollout 文件才是内容的唯一真相。** agenthud 的文档明确写了这点：*"these are caches / app state, not the conversation source of truth. The rollout JSONL holds full content."*

→ **Codex 没有对会话内容做 FTS/向量索引**。它的索引只解决"列出最近的会话"，不解决"搜索历史内容"。

### 2.3 上下文窗口怎么控制？—— **摘要压缩，不是截断**

- 触发：`model_auto_compact_token_limit`（token 阈值）+ 自动 compact
- 手动：`/compact` —— *"Summarizes visible conversation to free tokens"*
- 实现：openai/codex `codex-rs/core/src/compact.rs`，关键常量：
  ```rust
  const COMPACT_USER_MESSAGE_MAX_TOKENS: usize = 20_000;
  pub use codex_prompts::SUMMARIZATION_PROMPT;
  pub use codex_prompts::SUMMARY_PREFIX;
  ```
  → **是 LLM 摘要，不是滑窗截断**
- 两条路径：
  - 非 codex 模型：**本地** LLM 摘要（`SUMMARIZATION_PROMPT` + `SUMMARY_PREFIX` handoff 提示词）
  - codex 模型：调用服务端 `compact()` API，返回**加密 blob**，内部逻辑不公开
    - 证据：simzhou.com/en/posts/2026/how-codex-compacts-context/ —— 用 prompt injection 实测证明服务端确实有 compaction prompt 和 handoff prompt，且与开源版本"几乎一致"
- 官方维护者 etraut-openai 在 openai/codex#10823 确认：*"Until recently, Codex used a separate endpoint and server-side logic for compaction. We recently switched to a more robust approach where the compaction logic is moved locally using the same endpoint as normal turns."*
- 支持 `PreCompact` / `PostCompact` hook
- 证据：openai/codex `codex-rs/core/src/compact.rs` 源码 + u-ichi/compact-plus 架构文档（列出 Codex 的 `model_auto_compact_token_limit`、`compact_prompt`、`experimental_compact_prompt_file` 等配置键）

### 2.4 有没有淘汰老会话的命令？—— **有归档，但没有留存期配置**

- `~/.codex/archived_sessions/` 目录存在，archival 后的 rollout 移到这里（openai/codex#19362 的报错信息里能看到完整路径 `Error: Failed to resume session from ~/.codex/archived_sessions/rollout-...jsonl`）
- `state_5.sqlite` 的 `threads` 表有 `archived` / `archived_at` 字段
- **但没有找到任何"自动按天删除旧 rollout"的官方机制** —— 反而因此爆出了大量磁盘事故

### 2.5 Codex 的真实磁盘事故数据（**反面教材，必须看**）

| Issue | 数据 |
|---|---|
| openai/codex#24948 | 单个 rollout **732 MB**（170,415 行）。构成：`compacted` 记录 **337.8 MB**（684 条）、`function_call_output` 230.8 MB、`reasoning` 54.8 MB。`~/.codex/sessions` 总计 **91 GB**，184 个文件 >100 MB，最大 1.95 GB |
| openai/codex#42345 | 单个 rollout **1,446 MB**。**每条命令的输出被存了 4 份**（`stdout` / `aggregated_output` / `formatted_output` / `response_item` 副本），24,120/25,280 条 `aggregated_output` 与 `stdout` 逐字节相同。另有 365 条 `compacted` 记录平均 527 KB（188 MB），455 张 base64 PNG 截图内嵌（105 MB）。全目录 39 GB |
| openai/codex#34337 | 644 个 rollout 达 **70.23 GiB**；另有报告 122.2 GiB、135 GB、**755 GiB**、1.5 TB |

> **对用户场景最关键的一条结论**：Codex 的 `compacted` 记录会**把整份压缩后的历史重新嵌进每一条 compacted 记录里**——这正是 Hermes 用 `active` 布尔位 + 独立摘要行**刻意避开**的坑。openai/codex#24948 里 684 条 compacted 记录吃掉 337.8 MB，#42345 里 365 条吃掉 188 MB。**"压缩"本身成了最大的磁盘占用源。**

## 3. Hermes 自己怎么设计会话存储？

### 3.1 Schema（`hermes_state_common.py:461-563`）

**单文件 SQLite `state.db`**，WAL 模式（实测 `journal_mode=wal`, `page_count=80869`, `page_size=4096`, `freelist_count=10`）。

**`sessions` 表**（`hermes_state_common.py:461-527`）关键字段：

```sql
compression_failure_cooldown_until REAL,   -- 摘要 LLM 失败后的冷却截止时间
compression_failure_error TEXT,
compression_fallback_streak INTEGER NOT NULL DEFAULT 0,
compression_ineffective_count INTEGER NOT NULL DEFAULT 0,
compression_recovery_deadline REAL,
compression_overload_streak INTEGER NOT NULL DEFAULT 0,
archived INTEGER NOT NULL DEFAULT 0,
auto_archived INTEGER NOT NULL DEFAULT 0,
pinned INTEGER NOT NULL DEFAULT 0,
hidden INTEGER NOT NULL DEFAULT 0,
```

**`messages` 表**（`hermes_state_common.py:531-563`）关键字段：

```sql
active INTEGER NOT NULL DEFAULT 1,       -- 1=模型可见, 0=已归档
compacted INTEGER NOT NULL DEFAULT 0,     -- 1=被压缩归档
_compressed_summary INTEGER NOT NULL DEFAULT 0,  -- 1=这一行是压缩摘要
```

### 3.2 4400 万字符怎么压进上下文？—— **`active` 布尔位 + 摘要行**

这是 Hermes 最核心的设计，也是它与另外两家的分水岭：

| 层 | 实现 | 证据 |
|---|---|---|
| **模型装填** | `get_messages_as_conversation()` 默认只取 `active = 1` 的行 | `hermes_state_messages.py:1491-1508`，其 docstring 明说 *"``include_compacted`` (deduped display history) is for DISPLAY reads only: the model-fed restore must not regrow what compaction summarized away"* |
| **压缩归档** | 压缩后 `UPDATE messages SET active = 0, compacted = 1`（`_ARCHIVE_ACTIVE_SQL`，`hermes_state_messages.py:72`） | 同上 |
| **摘要落库** | 摘要作为**一条独立的 message 行**写入，带 `_compressed_summary=1` 标记 | `hermes_state_common.py:550`；`agent/context_compressor.py:5572-5576` 构造时打 `COMPRESSED_SUMMARY_METADATA_KEY` |
| **历史仍可搜** | FTS 搜索条件是 `(m.active = 1 OR m.compacted = 1)` | `hermes_state_search.py:169-174`，docstring: *"rows (active=1) AND compaction-archived rows (compacted=1) are discoverable"* |
| **显示层** | `include_compacted=True` 走 `_DISPLAY_ACTIVE_CLAUSE`，供 UI 展示完整历史 | `hermes_state_messages.py:56, 1340-1342` |

**压进上下文的实际算法**（`agent/context_compressor.py:5447` `compress()`）：

1. **Phase 1** — 先做无 LLM 的廉价裁剪：`_prune_old_tool_results()` 把老的 tool result 正文缩成摘要（不动 tool_call 参数）
2. **Phase 2** — `_compress_window()` 划边界：保住 **head**（系统提示 + 前 N 条，`protect_first_n: 3`）和 **tail**（按 token 预算从新往旧累积，`target_ratio: 0.2`、`protect_last_n: 20`）
3. **Phase 3** — 中段交给 LLM 生成结构化摘要（`_summarize_window`）；摘要在 `tail_mode: "lean"` 下会带 chunked digests、anchor index、verbatim user messages 和 session_search 指针
4. **Phase 4** — `_assemble_compressed()` = head + 摘要行 + tail

> **不是按 token 预算取最近 N 条**——是"廉价裁剪 → 摘要 → 重组"的完整压缩流水线。配置见 `hermes_cli/config_defaults.py:591-702`。

### 3.3 压缩确实在跑（推翻之前报告的结论）

**本机实测**：

```
summary rows:                54 条（_compressed_summary=1）
distinct sessions 有摘要:      5 个
messages total:              50,208
  active=1（模型可见）:       14,617
  compacted=1（已归档）:      27,407
```

按会话看：

| 会话 | active | compacted | 摘要数 |
|---|---|---|---|
| `<CHANNEL_ID>_13865a` | 816 | 9,946 | 1 |
| `<CHANNEL_ID>_db1b00` | 151 | 6,894 | 11 |
| `<CHANNEL_ID>_51947b` | 701 | 6,654 | 30 |
| `<CHANNEL_ID>_87a316` | 67 | 2,655 | 6 |
| `<CHANNEL_ID>_c902a0` | 245 | 1,725 | 6 |

**`docs/会话库-真问题.md` 说"压缩压根没触发过"，依据是 `auto_archived = 0` 和压缩失败计数全 0。这两个指标测错了对象**：

- `auto_archived` 是**会话级**的闲置归档标记，跟消息级压缩无关
- 压缩失败计数全 0 的真正含义是**压缩没失败过**（而不是没触发）
- 真正的证据是 `_compressed_summary` 行和 `compacted=1` 行——**27,407 条消息被压缩归档了，占全库 55%**

**推论**：Hermes 的「历史 ≠ 上下文」区分**不只是设计，是这台上机器正在发生的事实**。

### 3.4 压缩失败会怎样？—— 三个计数器，三种降级

| 字段 | 触发条件 | 失败时的行为 | 源码 |
|---|---|---|---|
| `compression_failure_cooldown_until` | 摘要 LLM 调用报错（无辅助 provider / 瞬时错误 / 配额） | **冷却期内跳过自动压缩**。错误文本写入 `compression_failure_error`。手动 `/compress` 会清冷却（`force=True`） | `agent/context_compressor.py:2606-2631`；`hermes_state_compression.py:491-498` |
| `compression_ineffective_count` | 压缩提交后被判定"没起作用"（压完还是超阈值 / 提交前被拒） | **≥2 触发熔断**（`_tripped()`），此后自动压缩被跳过；触发 `_ANTI_THRASH_RECOVERY_SECONDS` 反抖动窗口后允许**一次试探性压缩**（计数降回 1），失败则再次熔断 | `agent/context_compressor.py:3027-3034`（`_tripped`）、`3071-3119`（反抖动恢复）、`2495-2500` |
| `compression_overload_streak` | 连续过载（模型持续报 context 超限） | 递增；超过阈值后摘要失败**直接中止**而非退化为静态 fallback。任一成功的压缩边界会重置它（`_reset_consecutive_overload_aborts`） | `agent/context_compressor.py:2449-2476`、`2550-2551` |
| `compression_fallback_streak` | 压缩完成但用的是**确定性静态 fallback**（LLM 没调成功） | 递增；达到阈值后**把摘要模型"bench"掉**（`_fallback_streak_skip`），不再调用付费的辅助 LLM | `agent/context_compressor.py:2540-2549` |
| `compression_recovery_deadline` | 反抖动窗口的墙钟截止时间 | 持久化到 session 行，进程重启后**从同一窗口继续**，不会重置 | `agent/context_compressor.py:3077-3084` |

**两条硬规则**（`agent/context_compressor.py:5238-5269` `_abort_on_summary_failure`）：

1. **访问/配额错误、网络错误、截断、空内容 → 永远中止**，不降级
2. `compression.abort_on_summary_failure: true`（默认 `false`）→ 中段用"summary unavailable"占位符替代

> 中止的后果文档写得明白：*"the session **freezes at its size** until /compress (bypasses the cooldown) or /new"*（`hermes_cli/config_defaults.py:674-676`）。
> **这正是用户"上下文压缩会改变 agent 行为"担忧的技术根据**：压缩失败不是降级，是冻结。

### 3.5 `archived` / `hidden` / `auto_archived` 三字段的区别

| 字段 | 语义 | 触发条件 | 源码 |
|---|---|---|---|
| **`archived`** | **软隐藏**（消息一条不删）。默认列表不显示，但**仍可恢复、仍可搜索** | ① 用户/CLI/API 主动归档（`set_session_archived`，`hermes_state_sessions.py:951-965`）② 闲置清扫（`archive_stale_sessions`，`hermes_state_maintenance.py:306-331`） | 同左 |
| **`auto_archived`** | **归档来源标记**：`archived=1` 且 `auto_archived=1` = "闲置清扫干的"；`archived=1` 且 `auto_archived=0` = "有人故意藏的" | 主动归档时**清零** `auto_archived`（`hermes_state_sessions.py:960`）；闲置清扫时**只在 `archived=0` 时置 1**（`hermes_state_sessions.py:972-974`） | 同左 |
| **`hidden`** | **从默认列表里隐藏，但仍可 resume**。目前唯一用途是藏"Bot Chat"这个规范会话 | `set_session_hidden`（`hermes_state_sessions.py:1058-1060`）；Bot Chat 由 `gateway/session_hosted_rpc.py:110` 置 `hidden=1` | 同左 |

**`auto_archived` 的真正价值：区分"该自动恢复"和"不该自动恢复"。**

`_unarchive_auto_archived_lineage()`（`hermes_state_sessions.py:976-996`）的逻辑：

- 压缩或 resume 让 lineage 重新活跃 → **自动取消归档**
- 但只要 lineage 里**存在任何一行 `archived=1 AND auto_archived=0`**（= 有人故意藏的）→ **不自动恢复**，手动归档一直有效

> 换句话说：`auto_archived` 是"这条归档可以被机器撤销吗"的标志位。**人工与自动的分界做得很干净**，这是 Hermes 比另外两家细致的地方。

**相关字段 `pinned`**：持久"保留"标记，**豁免闲置清扫**，`set_session_pinned` 还会顺手清掉 `hidden`（`hermes_state_sessions.py:1041-1056`）。

**闲置清扫触发条件**（`hermes_state_maintenance.py:306-331` + `hermes_cli/config_defaults.py:2289-2293`）：

- `sessions.auto_archive: false`（**默认关**）+ `auto_archive_days: 3`
- 候选条件：`archived = 0` 且 `end_reason <> 'compression'` 且 未 pin 且 不是 Bot Chat，且最后活跃时间早于 cutoff
- 24 小时节流（`min_interval_hours`），`state_meta.last_auto_archive` 记录

### 4.3 重点：「历史 ≠ 上下文」这个区分，三家分别怎么实现

| | 存储层 | 上下文层 | 搜索层 | 一致性风险 |
|---|---|---|---|---|
| **Claude Code** | 同一份 JSONL，用 `type` 字段区分 `summary` 与普通条目 | 读时取 summary + 尾部 | 无索引（grep 全文件） | 低（同一文件，不可能不一致） |
| **Codex** | 同一份 rollout，普通记录 + `compacted` 记录并存 | 读时用 compacted 替换历史 | 无内容索引 | **高**（`compacted` 重复嵌历史，磁盘爆炸；且 compaction 只在本地/服务端二选一） |
| **Hermes** | **同一个 SQLite，但用 `active` 布尔位区分**，摘要独立成行 | 读时 `WHERE active = 1` | FTS 覆盖 `active=1 OR compacted=1` | **低**（单一数据源，触发器保证索引与表同步） |

> **Hermes 这套设计是三家里最稳的**：
> - 单一数据源 → 不存在"摘要文件"和"历史文件"不一致的可能
> - `active` 是普通列 → 可以直接 `WHERE` 过滤，不需要额外的解析逻辑
> - 摘要**独立成行**而不是嵌进历史 → 避免了 Codex 那种"每次压缩都把全量历史再存一遍"的放大
> - FTS 索引覆盖归档行 → "历史可搜"和"上下文干净"同时成立

**但它有一个短板**（第 5.3 节展开）：**压缩触发绑在单个会话的上下文占比上，而不是整个库的总占用上。** 对"一条会话跑到底"是对的；对用户"几百条会话、每条都不长"的用法，就显得各条会话都够不着阈值，库一直涨。

## 5. 对这台机器最合适的做法

### 5.0 先纠正基线：现在到底什么状态？

**实测（本机 `state.db`，2026-10-30）：**

| 指标 | 数值 |
|---|---|
| 文件大小 | 331,239,424 字节 = **315.7 MiB** |
| 会话数 | 148 |
| 消息数 | 50,208 |
| 消息总字符 | 44,733,034 |
| active=1（模型可见） | 14,617 条 / 18,185,090 字符 |
| active=0（归档，可搜） | 27,407 条 / 26,812,744 字符 |
| `_compressed_summary` 摘要行 | 54 条 |
| FTS 搜索 `MATCH` | **2.0 ms**（608 命中） |
| trigram 搜索 | **1.0 ms**（8,992 命中） |
| LIKE 全表扫 | **175.8 ms**（630 命中） |
| 会话年龄分布 | **全部 < 90 天**（最早 2026-08-07，最晚 2026-10-30） |
| `archived` / `auto_archived` / `hidden` / `pinned` | 4 / 0 / 1 / 0 |
| 压缩失败四计数器 | **全 0**（= 从未失败） |
| `fts_layout_drift()` | `['messages_fts_trigram']` |

**磁盘占用构成（`dbstat`）：**

| 对象 | 大小 | 占比 |
|---|---|---|
| `messages`（消息本体） | 133.71 MB | 42.3% |
| **`messages_fts_trigram_data`** | **115.43 MB** | **36.5%** |
| `messages_fts_data` | 25.68 MB | 8.1% |
| `state_meta` | 15.96 MB | 5.1% |
| `system_prompts` | 5.72 MB | 1.8% |
| 其余索引 | ~14 MB | ~4% |

**两个立刻可见的结论：**

1. **`hermes sessions prune` 在这台机器上是个空操作。** 默认 90 天，而最老的会话才 84 天。实测 `ended sessions older than 90d: 0`，能回收 **0 字节**。就算把 `--older-than` 调到 7 天，那 5 个"大贡献"会话（占了 2700 万字符里的 2.7 千万）也全在 30 天内，一刀下去就把用户的关键项目历史砍了。

2. **最大的可回收项是 trigram 索引，不是消息。** `messages_fts_trigram_data` 116 MB 里存的是 tool 调用的 JSON 参数（v1 布局多出的那列），而当前代码的 v3 布局已经不要它了。

### 5.1 候选方案

---

#### 方案 A：跑 `hermes sessions optimize-storage`（**推荐**）

**动什么**：把 `messages_fts_trigram` 从 v1 布局（content + tool_name + **tool_calls**）重建为 v3 布局（content + tool_name），然后 VACUUM。

**为什么有效**：`optimize_fts_storage()`（`hermes_state_search.py:658-728`）的 docstring 明确写了它处理两种情况：*"legacy-v22 inline → external-content, or a v23 `messages_fts_trigram` that still stores `tool_calls`"* —— **正是本机的状态**。

**实测回收（在 scratch 副本上做的，真库未动）**：

```
重建 trigram 为 v3 布局 + VACUUM：
  before: 315.7 MB → after: 223.4 MB
  回收 92.2 MB (29.2%)
  trigram 重建耗时: 2.9 s
```

**代价**：
- 磁盘空间：新旧索引并存 + VACUUM 需要约等于当前文件大小的空闲空间（`sessions_cmd.py:993-1000` 会做 preflight 检查）。本机 C: 盘剩 **269 GB**，毫无压力
- 时间：trigram 重建本身 2.9 秒，加上基础索引回填与 VACUUM，估 1–3 分钟
- 需要停 gateway / Desktop / cron 等所有持有 state.db 的进程（`--force` 可以绕过，但源码警告 *"rewriting the store under a live writer can leave every agent refusing turns until all writers are stopped"*）
- **改的只有索引，一条消息都不动**

**风险**：**低**。可中断、可续跑（`state_meta.fts_rebuild_high_water` 标记进度）。源码明确：*"Safe to interrupt and re-run — it resumes where it left off. No conversation data is changed; only the search index is rebuilt."*

**会不会丢信息**：**不会**。历史 100% 保留，搜索功能反而更快（索引变小）。

**副作用**：`sessions.cjk_fts` 为 true 但本机没有 `<CHANNEL_ID>.so`，重建后 CJK 搜索仍然走 trigram 兜底（不变）。

---

#### 方案 B：清理 `state_meta` 里的网关回执垃圾（**推荐，与 A 独立**）

**动什么**：`state_meta` 里 `gateway.admission.result.v1.*` 键累积了 114 行、13.6 MB 的**网关回执**（每行是完整的一轮对话结果快照）。

**实测回收**：

```
删除 114 行 gateway.admission.result% + VACUUM：
  before: 315.7 MB → after: 296.6 MB
  回收 19.1 MB (6.0%)
```

**代价**：极低。但**这是手工 SQL，官方没有对应子命令**——需要自己判断这些回执是否还有用（它们是网关的重放依据，删掉可能导致某个进行中的 turn 无法重放）。

**风险**：**中低**。建议先备份 state.db 再操作。

**会不会丢信息**：删掉的是**网关内部回执**，不是对话内容。对话本体（`messages`）完全不受影响。

**更好的做法**：先查有没有官方维护的清理路径（`hermes sessions stats` 或 `doctor` 会报），再决定是否手工删。

---

#### 方案 C：归档（软隐藏）久未活动的会话（**不推荐现在做**）

**动什么**：`hermes sessions archive` —— 软隐藏，**不删数据**，随时可取消。

**为什么现在不推荐**：
- 本机**只有 4 个会话**被归档（`archived=1`），**0 个**是自动归档（`auto_archived=1`）
- `sessions.auto_archive` 默认是 `false`，`auto_archive_days: 3`
- 148 个会话里绝大多数是 cron 任务产生的（`助手榨干器-*`、`怀恩项目-定时检查-*`），它们有固定产出节奏，"闲置"判定意义不大
- **回收不了空间**（归档不删数据，磁盘占用不变），只是让列表干净

**什么时候值得做**：会话列表太长影响找老会话时。**当作"整理"而不是"优化"**。

**风险**：低（可逆）。**不丢信息**。

### 5.2 ❌ 这个场景下**不该做**的做法

| 不该做 | 理由 | 证据 |
|---|---|---|
| **`hermes sessions prune`（删老会话）** | **回收 0 字节**（全部会话 < 90 天），却会砍掉用户的关键项目历史。而且被删会话的 `parent_session_id` 会被置 NULL、消息全删 | 实测 `ended sessions older than 90d: 0`；`hermes_state_maintenance.py:395-397` |
| **手工 `DELETE FROM messages WHERE active=0`** | 能回收 45.4 MB（14.4%，实测），但删掉的正是**用户唯一的历史副本**——active=0 只是"不送进模型"，不是"没用"。删了就搜不到了 | 实测回收 45.4 MB；`hermes_state_search.py:174` 证明这些行正是 FTS 可搜的部分 |
| **删 `system_prompts` 去重** | 101 行 / 4.8 MB，且 101 行内容**互不相同**（`count(distinct prompt) = 101`），去不了重。删了会让对应会话下次重建系统提示 | 实测 |
| **改 `compression.threshold` / `abort_on_summary_failure` 来"优化"** | 这会**改变 agent 行为**。压缩失败时 Hermes 是"冻结会话"（`sessions frozen at its size until /compress or /new`），不是降级。把 `abort_on_summary_failure` 打开会让压缩失败从"用静态 fallback 继续"变成"整段历史卡住" | `agent/context_compressor.py:5238-5269`；`hermes_cli/config_defaults.py:674-676` |
| **开 `auto_prune`** | 这是**删数据**，默认 `false` 是有意的设计（源码注释：*"deleting history is opt-in"*）。用户的历史关联不应该被自动清 | `hermes_cli/config_defaults.py:2283-2286` |
| **动 `sessions.retention_days`（90 天）** | 本机所有会话都在 90 天内，改这个数对现状零影响，只是给未来埋一个删除定时器 | 实测 |
| **跑 `VACUUM` 单独做** | 只回收 **3.9 MB（1.2%）**，因为 freelist 只有 10 页。SQLite 删行不还盘是常态，但本机几乎没删过东西，所以没什么可回收 | 实测 |

### 5.3 那个"最值得改"的设计点（但**不该现在改**）

`docs/会话库-真问题.md` 提的方向是对的，我补一个精确的证据和一条反对意见。

**方向对**：Hermes 的压缩触发绑在**单个会话的上下文占比**（`compression.threshold: 0.5`）上，不是**整个库的总占用**上。对"一条会话跑到底"是对的；对"几百条会话、每条都不长"的用法，各条会话都够不着阈值 → 库一直涨。

**但本机证据不支持"压缩没触发"**：
- 压缩实际触发了 27,407 次（消息级归档），54 次摘要生成，分布在 5 个会话上
- 5 个会话正是那几个"超大"的（6,894 / 9,946 / 6,654 / 2,655 / 1,725 条归档）
- **说明压缩器工作正常，触发得也准**——大会话被压了，小会话（cron 那种 300–400 条）确实够不着阈值

**那这算不算问题？** 算，但优先级不高：
- 单个 cron 会话 402 条消息 / 569,699 字符 ≈ **162,771 tokens**——**已经超过很多模型的上下文窗口**，也会触发压缩（只是阈值取决于模型窗口大小）
- 真正的浪费在于：**这些 cron 会话每个都独立攒了 40–60 万字符的历史，且几乎不会被再次打开**

**最省事的对症方案**（比改压缩器安全得多）：
> 让 cron 任务**每次跑完开新会话**（而不是复用同一个 session_id），老会话自动归档。
> 归档不删数据 → 用户想搜还能搜；列表干净；库的增速自然趋缓。

这条**不动任何 Hermes 源码、不改配置**，只需要在 cron 任务定义层面处理。
