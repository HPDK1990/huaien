# 架构

## 分层

```
┌─────────────────────────────────────────────┐
│  前台  huaien/app.py                          │
│  纯黑单对话框 / 打字机 / 无按钮               │
└──────────────┬──────────────────────────────┘
               │  ask(msg, on_text, on_done, on_error)
┌──────────────▼──────────────────────────────┐
│  桥接  huaien/bridge.py                       │
│  起进程 → 读 stream-json → 回调               │
│  记住 session_id, 下一轮 --resume             │
└──────────────┬──────────────────────────────┘
               │  subprocess
┌──────────────▼──────────────────────────────┐
│  后台  Hermes Agent (profile: huaien)         │
│  人格 = profiles/huaien/SOUL.md                │
│  工具 / 日志 / 看板 / 任务卡 — 全部在这里       │
└─────────────────────────────────────────────┘
```

## 为什么用 CLI 而不是 RPC

Hermes 的 gateway 暴露的是 JSON-RPC/WebSocket(桌面 app 用), 方法名与参数契约
不在公开文档里, 直接摸要花很多时间且容易脆。
`hermes chat` 是 Hermes 最稳定的接口面, 契约稳定、输出格式有保证(`--format stream-json`),
而且 `--resume` 原生支持多轮。

**代价**: 每轮 2-4 秒进程启动开销。对一个"话不多"的管家界面, 可以接受。

## 为什么用独立 profile

后台工程用的 profile 带着完整的格式契约(SOUL.md 里有"必须带自检行"之类),
那是给工程师看的, 不适合前台。独立 profile 让前台是"管家", 后台是"工程师", 互不污染。

## 关键约束

- 前台**只**显示对话。工具调用、执行过程、任务卡、日志一律不进界面。
- 前台**不**保存明文凭据。所有鉴权走 Hermes 自己的凭据管理。
- 前台的会话 id 只留在内存里。Esc 清空即丢弃。
