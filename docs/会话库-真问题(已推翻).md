> 你给的优化方案我感觉都不好。先看看大家是怎么弄的。"*

**用户的直觉是对的，我上次的两个方案都打偏了。**
本文先摆事实，Claude/Codex 的横向对比见
`docs/调研-会话存储对比.md`（调研中）。

## 一、实测：库大，但查询一点都不慢

```
state.db  314.4 MB | 50134 条消息 | 147 个会话 | 4400 万字符

全表 COUNT(*)            2.0 ms
FTS5 全文索引搜索        1.0 ms
LIKE '%关键词%' 全文扫   150.6 ms
sessions 全表排序         1.3 ms
```

**数据库查询全部毫秒级。** 因为有 FTS5 索引，搜索根本不走全表。

## 二、真问题：压缩机制**从来没有在这个库上触发过**

Hermes **自带 2700+ 行的上下文压缩器**（`agent/context_compressor.py`），
而且 `_compression_codex_settings` 明确**参考了 Codex 的做法**。

### 当前配置（`config.yaml` 第 55-69 行）

```yaml
compression:
  enabled: true                     # 压缩开着
  threshold: 0.5                    # 上下文用量到 50% 才触发
  target_ratio: 0.2                 # 压完留 20%
  protect_last_n: 20                # 保护最近 20 条
  protect_first_n: 3                # 保护最早 3 条
  max_attempts: 3
  proactive_prune_tokens: 0         # 主动裁剪兜底: 关着
  proactive_prune_min_reclaim_tokens: 4096
  idle_compact_after_seconds: 0     # 空闲自动压缩: 关着
  codex_gpt55_autoraise: true
```

### 但库里的证据是：

```
sessions 分布:
  活跃 · 手动      144 个, 48805 条消息
  已归档 · 手动      4 个,  1488 条
  auto_archived       0 个      ← 压缩从未自动归档过任何一个会话

压缩失败计数 (148 个会话全部):
  compression_failure_cooldown_until = None
  compression_ineffective_count      = 0
  compression_overload_streak        = 0
```

**压缩失败计数全是 0，auto_archived 也是 0** →
**不是"压缩失败"，是"压缩压根没触发过"。**

### 为什么没触发

**关键：压缩是按「单个会话的上下文占用」触发的，不是按「库的大小」。**

144 个会话平均 340 条消息，**每个会话单独看都没到 50% 阈值** →
库一直涨，但**没有任何一个会话需要压缩** → 压缩器一直闲着。

**所以"库大"和"会慢"是两件事**，我上次把它们混为一谈了。

## 三、那"会越来越慢"到底怎么来的

| 场景 | 会不会慢 | 为什么 |
|---|---|---|
| 打开任意旧会话、翻历史 | ❌ 不会 | FTS 搜索 1 ms |
| 在**当前这个长会话**里继续聊 | ✅ **会** | 这个会话已经 492 条消息，历史一直往上下文里堆，迟早撞上 50% 阈值 → 触发压缩 → 摘要 |
| 备份整个库 | ⚠️ 线性变慢 | 314 MB 备份要 96 秒，再涨一倍就 3 分钟 |
| 启动 / 加载 | ⚠️ 轻微 | 会话索引变多 |

**结论：真正会变慢的是「在一条长会话里一直聊」，不是「库变大」。**

## 四、所以我上次的两个方案为什么都不对

| 我上次的方案 | 为什么不对 |
|---|---|
| `optimize-storage` 重建索引 | **只省磁盘，一点速度都不解决** —— 用户说"感觉都不好"精准命中 |
| `sessions prune` 删老会话 | **删的是用户的历史关联**，而且**跟内置压缩机制对着干**（压缩自己会归档父会话，手动 prune 是重复劳动 + 有丢信息的风险） |
| "上下文太长 → 变慢变贵" | **方向对但没落到点上** —— Hermes 已经有压缩器管这件事，问题是**它没触发**，不是"没有压缩" |

## 五、那么该做什么（三条，按优先级）

### 优先级 1：让压缩真的能跑（治本）

现在的配置有两个开关是关的：

| 开关 | 现在 | 含义 |
|---|---|---|
| `idle_compact_after_seconds` | `0` | 空闲 N 秒后自动压缩 —— **关着**，用户长时间不来时会话就一直堆 |
| `proactive_prune_tokens` | `0` | 压缩失败后的兜底裁剪 —— **关着** |

**这就是"该优化的地方"**：不是删库，是**把内置的压缩机制打开**。

### 优先级 2：长会话用 `/new` 开新会话，把老会话沉淀进 memory

Hermes 的记忆系统（`memories/`）本来就是干这个的。
一条 492 消息的会话该拆了 —— **老的历史进 memory，新的会话轻装上阵**。

### 优先级 3：`optimize-storage` 只在"磁盘紧张"时做

**它是磁盘优化，不是性能优化。** 314 MB 不急，268 GB 空闲。
等真到 800 MB 以上再说，跑一下也就 2-5 分钟。

## 六、Claude / Codex 怎么做的

见 `docs/调研-会话存储对比.md`（调研中，出来后再做批判性修改 + 落地）。

**先立一条待验证的关键区分**：
> **「历史」不等于「上下文」** ——
> 历史完整存下来（供搜索/审计），但只把摘要 + 最近几轮送进模型。

Hermes 有压缩器（说明它认同这个区分），但**触发条件绑在"单个会话的上下文占用"上**，
不是绑在"库的总大小"上 —— 这个设计对"单会话跑很久"是对的，
对"用户这样开几百条会话、每条都不长"的用法**不划算**。

**这可能是 Hermes 在这个使用场景下最值得改的一点**，等对比报告出来再定。
