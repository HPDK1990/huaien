# 上架隔离 —— 上传的和日常用的怎么分开

> 用户 2026-11-04 的问题:
> **"上传的和我用的测试的如何分开, 不可能每次上传前都要这样清一遍把。"**

## 结论：一句话

**不用清。** 开发环境保持原样，发布时用 `scripts/export_public.py` **导出一份干净的副本**，
只把副本推 GitHub。两份物理分离，**你日常怎么写都不影响**。

```
<PROJECT_ROOT>                ← 你的开发环境 (真实昵称 / 真实路径 / 真实配置)
     │  scripts/export_public.py  ← 导出时自动脱敏 525 处
     ▼
<PUBLIC_DIR>                 ← 干净的公开副本 (审计 rc=0, 可直接 push)
```

## 日常 vs 发布

| | 日常开发 | 公开版 |
|---|---|---|
| 位置 | `<PROJECT_ROOT>` | `<PUBLIC_DIR>` |
| 昵称 | 真实称呼 | 中性称呼 |
| 路径 | 本机绝对路径 | 占位符 |
| 会话 ID / 令牌 | 真值 | 占位符 |
| 内网 IP | 真值 | `192.168.x.x` |
| 要不要清 | **不用** | 导出时自动清 |

**你的开发环境永远不需要"干净"。** 那是你的工作区，不是发布物。

## 怎么用

```bash
# 导出 + 自动审计 (推荐, 一条命令)
python scripts/export_public.py --out ..\huaien-public --audit

# 只看会改什么, 不写盘
python scripts/export_public.py --dry-run

# 一键导出 + 提交 + 推送
python scripts/publish_release.py
```

`publish_release.py` 会：导出 → 审计（rc 必须 0）→ git init/commit → push。

## 三道闸（都在公开版这一侧）

| 闸 | 位置 | 作用 |
|---|---|---|
| 1. **导出器** | `scripts/export_public.py` | 生成副本时脱敏 525 处 |
| 2. **审计器** | `scripts/audit_publish.py` | 扫描副本，rc≠0 不许推 |
| 3. **CI** | `.github/workflows/audit.yml` | 远端强制，别人 fork/PR 也挡 |

开发仓库那侧还有一个 **pre-commit 钩子**（`scripts/install_audit_hook.py`）——
它拦的是**开发仓库自己**，防止你自己手滑把真值 commit 进历史。

## GitHub 官方手段（调研结论）

GitHub 自带的 **Push Protection** 会在 push 时挡下硬编码凭据。但：

- 仓库级开关需要 **GitHub Secret Protection**（个人公开仓不一定有）
- **用户级**的 push protection 默认开启，能挡往公开仓推的常见 key
- **但它只认"已知 provider 的凭据形态"** —— 昵称、机器路径、内网 IP、
  你的微信 chat_id，**它一个都不管**

所以 GitHub 的工具**不能替代**本项目这套。官方定位是"最后一道网"，
我们要的是"源头就不产生"。

📌 官方文档：
- [Push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection)
- [从存储库中删除敏感数据](https://docs.github.com/zh/enterprise-cloud@latest/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

## 脱敏规则在哪改

`config/publish_rules.json`（不存在则用 `scripts/export_public.py` 里的 `DEFAULT_RULES`）。

规则是 **正则 + 替换模板**，不是硬编码的真值。
改规则不用改代码，加一条就生效。

| 组 | 内容 |
|---|---|
| 昵称 | 真实称呼 → 中性称呼 (用户 / 助手) |
| 机器路径 | `<USER_HOME>` → `%LOCALAPPDATA%`；`<PROJECT_ROOT>` → `<PROJECT_ROOT>` |
| 真实标识 | 飞书 chat_id / AppID / open_id、微信 chat_id、访问令牌、session 引用 |
| 网络 | 内网 IP → `192.168.x.x` |

## 审计器的两个坑（踩过才知道）

**1. 不能靠"猜内容"判断真假凭据。**

曾经的错误做法：看结尾是不是 `abc` 连续序列 → 是就当夹具放过。
**结果：一个真实 key 被放过了**（真 key 随机，尾部也可能有连续字母）。
猜宽了漏真凭据，猜窄了误报夹具，两头都是坑。

正确做法：**靠上下文**——
① 值是一眼可辨的占位符（`xxx` / `<TOKEN>` / `YOUR_KEY`）→ 豁免
② 在**测试文件**里 + 带常见假前缀 + 内容有 ≥10 位连续段 → 豁免
③ 其他一律报

判据由 `tests/test_audit_publish.py` 双向锁死：**真凭据必报**（在源码和在测试文件里都必报），
**夹具不误报**。

**2. 长度不能写死。**

`AIza[A-Za-z0-9]{35}` 这种定长规则会让**39 位的真 Google key 完全不匹配**（漏报），
而长度刚好 35 的测试夹具反被报出来（误报）。所有 key 规则都用**变长**。

## 豁免清单（都是"看一眼就确定不是真值"的）

| 形态 | 为什么豁免 |
|---|---|
| `xxx` / `<TOKEN>` / `%LOCALAPPDATA%` | 一眼占位符 |
| `git@github.com:HPDK1990/...` | **公开仓的地址**，必须有 |
| `xxx@im.bot` / `<ILINK_BOT_ID>` | Hermes 源码文档里的官方示例 |
| `<CHANNEL_ID>` | 占位 id |
| `[[FILE:E:\\完整\\路径\\...]]` | 文档里举例说明路径写法 |
| 测试文件里的 `<ANTHROPIC_KEY>` | 测试夹具，公开仓必须有测试 |

⚠️ 豁免一律**有上限**：真凭据在**任何位置**（包括测试文件）都必须被报。
